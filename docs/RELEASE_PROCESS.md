# 发布流程

本流程用于 2.x 预发布和正式版本，目标是保证代码、标签、发行包、文档、在线更新和 1.x 迁移入口保持一致。

## 1. 冻结版本范围

- 当前版本范围达到内部验收标准。
- 未完成工作不得混入本次发布。
- 不在发布候选阶段临时加入无关功能。

## 2. 发布前更新

- 更新 `VERSION`。
- 将 Changelog 中对应版本从 Unreleased 改为发布日期。
- 更新 README 安装示例和版本文字。
- 更新项目总结、兼容性和实机验证记录。
- 确认 1.x 迁移助手仍指向当前已经存在的公开 Release；不要提前指向尚未发布的版本。

## 3. 验证候选提交

```bash
./tests/run.sh
./scripts/build-release.sh
sha256sum -c dist/<发行包>.sha256
git diff --check
```

- 在目标 Linux VPS 上解压同一归档并运行测试。
- 按该版本的内部验收清单完成高风险实机测试。
- 确认工作区干净，候选包来自准备合并的准确提交。

## 4. Pull Request 和 CI

- 使用功能分支创建 PR 到 `main`。
- PR 说明范围、安全影响、测试结果和非目标。
- 等待全部必需检查通过。
- 合并后确认 `main` 的树与已测试候选内容一致。

## 5. 创建 Release

- 从合并后的 `main` 创建版本标签。
- 预发布版本标记为 Prerelease。
- 上传版本化归档和 `.sha256` 文件。
- Release Notes 说明用户可见变化、安全边界、兼容性和已知限制。
- 检查 GitHub 显示的资产摘要与本地一致。

## 6. 发布后验证

- 从公开 URL 下载两个资产并验证 SHA-256。
- 在隔离环境验证全新安装。
- 从上一 2.x 版本执行真实在线更新。
- 检查安装后 SSH、UFW、Fail2Ban 和 doctor 状态。

## 7. 更新 1.x 迁移入口

只有新 Release 已公开并通过下载验证后，才能在后续小型 PR 中更新根目录 `vps_secure.sh` 的默认迁移目标。

该 PR 需要：

- 更新迁移目标版本；
- 更新迁移测试；
- CI 通过；
- 合并后确认原始下载入口可发现新版本。

## 8. 发布完成记录

- 将发布后发现的问题建立 Issue，不直接改写已发布历史。
- 需要替换已发布资产或移动标签时视为异常事件，必须说明原因并重新完成验证；正常情况下不覆盖既有 Release。
