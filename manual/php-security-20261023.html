2. PHP 应该更新到哪个版本？

PHP 官方 10 月 21 日公告涉及 CVE-2026-109618 与 CVE-2026-109619，影响处理 Web 请求的 PHP，包括 FPM、mod_php、CGI、FrankenPHP 和 LiteSpeed。具体可利用条件不同，不代表每台机器已被攻击。见 PHP 官方公告及 OOM 公告、全局状态公告。

上游分支上述两个 CVE 的修复版本
8.28.2.35
8.38.3.36
8.48.4.27
8.58.5.12

这是本事件的上游修复基线，不是所有漏洞已修复的保证，也不是永远最新版本。同分支更新优先；不要为了表中版本静默跨大版本。发行版可能回移补丁，必须按系统发行版、软件来源及完整包版本查公告，不能只比较上游数字。

例如 Ubuntu 的 109618 状态页列有保持旧上游号的修复包；还必须分别核对 109619 状态。Debian 同样分别查看 109618和 109619，不能把一个发行版的版本阈值套到第三方仓库。

PHP 8.1 及更旧分支已结束上游支持，但不等于完全没有修补途径：发行版、LTS 供应商可能提供回移修复；PHP 团队也为 7.4／8.0／8.1 提供了最小源码回移材料。源码补丁需要构建者验证，不恢复上游长期支持，也不是推荐普通用户现场手工打补丁。

10 月 23 日另有 CVE-2026-115560 提醒。官方建议在后续常规 bugfix 发布前关闭 session upload progress；适用条件与如何处理见第 8 节。不要只因已到上表版本就忽略它。

3. 不知道有没有 PHP：先做这一步

  1. 用面板管理服务器：打开面板的网站列表，看看有没有 WordPress、Laravel 或标为 PHP 的网站；同时检查已安装应用和运行环境。有这类项目，就需要核对 PHP；网站列表为空，也不能排除独立安装的应用。
  2. 确认这台机器从未安装 PHP，也没有 PHP 网站或应用：不需要为这次 PHP 预警专门安装或升级 PHP。这个判断只针对本次 PHP 问题。
  3. 不确定：Debian／Ubuntu 可展开下面的软件包查询。没有结果仍不能排除 Docker 或手工安装；把情况交给安装者确认，不把“没查到”当成“已修复”。

在 SSH 登录后的 VPS 终端执行下面的查询，不是在 Mac 本机终端，也不是在 vps 菜单的数字选择框里。若正在菜单中，先按菜单提示返回并退出，看到服务器的命令提示符后，再完整复制代码块执行。查询不会安装、更新或重启服务。

给维护者：如何确认查到的是网站正在使用的 PHP
要确认什么能证明什么不能替代什么
已安装的包／构建完整包版本、来源及对应公告；镜像构建记录／摘要磁盘已更新，不证明旧进程已退出
运行中的 worker具体 FPM 池、Apache／其他运行实例，实际加载的构建及替换证据服务显示 active 或 PID 改变，不单独证明补丁正确
网站路由映射网站→虚拟主机→FPM socket／上游容器或 Apache 模块→实例命令行 PHP、另一个网站或另一个容器的结果

先用已有面板和部署清单逐站核对绑定关系。Nginx 的 FastCGI 目标、Apache 的模块／代理处理方式应由管理员在本机确认；不要公开完整配置或运行会泄露敏感字段的全量配置转储。共享运行环境、多个池、多副本、停用但能自动拉起的旧实例都要登记。

展开命令：查询 Debian／Ubuntu 已安装的 PHP 软件包

仅在目标 Linux 主机已授权终端中使用可信系统工具。只列包名、完整版本和安装状态，不运行 PHP。失败显示“证据不足”；无输出仅表示该包清单未匹配，不能排除容器或自编译。

(
  if php_package_rows=$(LC_ALL=C dpkg-query -W -f='${binary:Package}\t${Version}\t${db:Status-Status}\n' 2>/dev/null); then
    printf '%s\n' "$php_package_rows" | awk -F '\t' '$1 ~ /^(php([0-9.]|[-:]|$)|libapache2-mod-php)/ { print }'
  else
    printf '证据不足：包清单查询失败。\n' >&2
    exit 1
  fi
)

结果怎么读：每行依次是“软件包名、完整版本、安装状态”。例如 php8.2-fpm　8.2.x-…　installed 表示安装了 PHP 8.2 的网站运行组件；这里只是格式示例，不是安全版本。installed 才表示已安装；其他状态或只有 CLI 命令行包，仍需核对网站实际使用什么。

下一步：有 PHP 包 → 继续系统软件包路线；没有输出或报错 → 继续核对面板／Docker，或用协助清单联系安装者。不要为让查询“有结果”而安装 PHP。

Linux：有限只读进程名称线索

不输出完整命令行。名称会截断或被修改；Apache 可能不加载 PHP，php 也可能只是 CLI。本命令不能识别版本、证明网站绑定或覆盖所有运行环境。无权限、进程命名不同及其他 PID 命名空间均可能漏检。

(
  if php_process_rows=$(LC_ALL=C ps -eo pid=,ppid=,comm= 2>/dev/null); then
    printf '%s\n' "$php_process_rows" | awk '$3 ~ /^(php|php-fpm.*|apache2|httpd|lsphp.*|frankenphp)$/ { print }'
  else
    printf '证据不足：进程查询失败。\n' >&2
    exit 1
  fi
)

不要公开 phpinfo 页面。不要上传 .env、私钥、数据库密码、完整日志、容器 Env 或含凭据的 argv。证据只需组件类型、包／构建版本、修复公告、实例数和核验状态；站点与实例身份留在本地。

4. 修改前先准备恢复能力

  1. 保留可用 SSH 和服务商控制台；确认操作对象与维护窗口，通知共享该 PHP 实例的网站使用者。
  2. 备份网站代码、上传数据、数据库和对应 PHP／Web／面板配置；记录原包来源、镜像摘要、扩展及配置挂载。备份加密或限制权限，不放进公开网站目录。
  3. 确认能恢复，并在隔离环境验证应用、扩展、数据库驱动与同分支安全更新兼容。备份存在不等于已验证恢复。
  4. 确认所有站点与实例映射。包安装脚本可能自动重启服务，不能把升级命令当成无中断操作；容器重建同样会影响请求。

任何软件源认证、签名、网络或依赖错误都应先处理，不跳过签名校验、不静默换源、不执行通用一键 apt upgrade。本指南不修改 Caddy、网络、防火墙或节点配置。

5. 用命令安装的 PHP：先查清包名，再更新

适用：Debian／Ubuntu 中用 APT 安装的 PHP。若网站的 PHP 在 1Panel 或 Docker 容器里，请改走面板／容器路线。这里的命令不会更新容器内 PHP。

  1. 在服务器 SSH 终端执行第 3 节的软件包查询，保留完整包名和版本。
  2. 复制下面命令，查看系统版本。它不会修改系统。
cat /etc/os-release

找到 ID 和 VERSION_ID 两行，例如 ID=debian、VERSION_ID="13"。

接下来需要核对软件来源和可更新版本。不同系统可能在旧版本号上补安全修复，所以不能仅凭“8.2 比 8.5 小”就升级大版本。把系统版本、完整 PHP 包清单交给维护者，使用下方流程核对；不确定时直接使用协助清单。

这里暂时没有适用于所有机器的一键升级命令。尚未确定你的网站对应哪个 PHP 服务、包来自哪里时，不能安全地给出完整更新命令。这条路线目前能完成信息收集；执行升级需要针对该机器确认包名和服务名，不能算作已完成修复。
给维护者：定向更新流程
  1. 确认网站使用的 PHP 分支、服务和扩展，核对软件来源与发行版公告中的完整修复版本。
  2. 完成备份后，在维护窗口刷新软件包索引；有源错误先处理，不使用过期索引判断无更新。
  3. 用 apt-get -s install --only-upgrade 加上已确认的包名列表模拟更新。这只是命令格式，不能直接照抄；确认不会删除必要组件或跨 PHP 分支后，再执行对应的定向升级。
  4. 按第 8 节核对配置。让实际处理网站请求的 PHP 服务加载新版本：FPM 更新对应 PHP 服务，Apache 内嵌 PHP 更新对应 Apache 服务。仅重启 Nginx 无法替代这一步。
  5. 确认原来的 PHP 进程已退出、新进程加载了修复版本，然后进行网站验证。

参考 APT 官方手册。本页未在你的服务器上执行这些变更。

6. 1Panel：PHP 更新入口在这里

在哪里操作：电脑浏览器里的 1Panel 后台，不是 vps 菜单，也不是 SSH 命令窗口。以下依据 1Panel 2026-10-22 升级公告整理；不同版本的布局可能不同，尚未逐版实机验证。

  1. 先找对网站。进入“网站”，打开要处理的网站设置，记下它使用的 PHP 运行环境名称和版本。一个环境可能供多个网站使用，把这些网站一起记下。
  2. 先备份。保存网站文件、数据库、PHP 配置和扩展列表，确认可以恢复。选择网站访问较少的时候操作，下面的更新和重启可能短暂中断网站。
  3. 刷新版本列表。进入“应用商店”，点击“更新远程应用”。这一步只刷新可选版本，不代表 PHP 已更新。
  4. 选择 PHP 版本。打开刚才记录的 PHP 运行环境配置，在版本下拉框里选择同一分支的修复版本。例如正在使用 8.2，就核对 8.2.35 或该分支更新的安全版本；其他分支看版本表。这一步不是去升级 1Panel 面板本身。
  5. 保存并重启对应服务。按面板提示完成运行环境更新，确认没有报错。仅选好版本、拉取镜像或更新应用列表都不算完成。若找不到相同入口，或者没有目标版本，停止在这一步，用协助清单求助，不要删除运行环境重装。
  6. 检查附加配置与网站。查看第 8 节的上传进度设置，再按第 9 节测试每个关联网站。后台出现新版还需核对实际运行实例，不能单靠版本下拉框宣布修复完成。

还在用 PHP 8.1 或更旧版本？先查 1Panel 公告对该分支的 patched 镜像说明，并确认你的环境适用。不要直接跳到 8.5；老网站可能不兼容。无法确认就让安装者协助处理。

自己管理 Docker／Compose 的用户

先确认哪个容器提供网站的 PHP，备份数据库、配置和挂载数据。按原部署方式选择已包含补丁的镜像，重新创建对应容器，并确认所有副本都使用了新镜像。不要直接替换其他来源的镜像。

拉取镜像只是下载；需要通过重新创建容器使用它。宿主机 APT 更新、下载成功、重启旧容器都不能证明容器内 PHP 已更新。不要对整个项目盲目执行 down。

需由维护者核对实际镜像构建、所有运行副本和网站绑定关系；配置修改也必须进入容器实际使用的 PHP 配置。不能确认时用协助清单，不要猜镜像名执行替换。

7. 自编译、其他面板与未知来源

交由负责该运行环境的维护者，从官方修复源码或有明确修复声明的供应商构建生成替代版本，在隔离环境完成编译、扩展与应用回归，再按原部署方式切换和替换 PHP 工作进程。保留构建版本、补丁来源、摘要及切换记录。不要在生产机器下载不明脚本，不执行未知路径的 PHP 来“测版本”。

旧分支按上游 EOL、发行版／LTS 支持、最小源码回移分别判断；不要自动从旧分支跳到 PHP 8.5。只有源码版本号、文件名或口头“已打补丁”而无法对应运行构建时，不标为已完成。普通用户应让供应商给出具体公告、包／镜像版本、切换方法与恢复方案。

8. 更新之外，还要检查一个上传进度设置

在哪里改：网站实际使用的 PHP 配置文件。1Panel 用户从对应网站／运行环境的 PHP 配置入口查找此项；找不到入口时，把下方配置行交给维护者，不要粘贴进终端。修改前保存原配置，修改后需让对应 PHP 服务重新加载配置，并验证网站上传功能。

PHP 官方指出，罕见组合涉及配置使用 php_binary 或 php_serialize，应用再于 session_start() 前用 ini_set() 切到 php，且上传进度仍启用；关联 CVE-2026-115560，完整公告随后续常规版本发布。见10 月 23 日官方原文。

对于不确定应用是否会切换处理器的用户，按官方建议在相应 Web PHP 的启动配置中设置：

session.upload_progress.enabled=0

这是 php.ini 配置行，不是终端命令。管理员应先备份实际生效配置，确认使用的是 FPM、Apache 还是容器内的配置，并采用该运行环境支持的管理方式。不要依赖应用内 ini_set() 或 FPM 的 .user.ini 作为请求解析前的防护。处理后需确认全部旧 PHP 工作进程 退出、设置对实际 Web 请求生效。CLI 的设置不能证明 Web 配置生效。

该项关闭的是 PHP 会话上传进度跟踪，不等同于禁止文件上传，但依赖此功能的应用进度展示可能受影响，必须测试。已按先前公告关闭并确认实际生效的，保留该设置；官方说明从不在运行时切换处理器的应用可保留功能，但不能靠猜测确认代码行为。后续解除缓解前重新阅读官方公告，不能按日期自动恢复。

这项设置不是 10 月 21 日两个 CVE 的完整修复替代品。仍须更新；WAF、隐藏错误、请求限制或一次测试都不等于完整修复。不要一键设置 memory_limit=-1：它会改变资源边界，也不能覆盖底层分配失败；如无法及时更新，应由维护者按两份 GHSA 逐项评估临时措施。

9. 做完后，怎样确认成功？

先在浏览器打开每个关联网站，实际完成一次登录、进入后台、提交表单，以及上传一张允许的测试图片（有这些功能时）。如出现白屏、502 或上传失败，先停止继续改动，保存错误提示并联系维护者。

网站能打开只说明业务可用。还要由维护者确认下面的补丁与配置已经生效，才能把本次处理记为完成。

  • 包／构建：对应来源明确覆盖两个 CVE；10 月 23 日的上传进度提醒也已单独处理或有可核实的不适用依据。
  • 全部实例：每个实际 网站 PHP 工作进程、容器副本和可自动拉起的部署定义均已核实；磁盘新版但进程旧、映射不明或无权限都记为未完成。
  • 真实业务：检查目标网站首页、登录、会话、表单、上传／导入、后台及相关任务；观察错误率和资源占用。不能用静态首页 200 或 CLI 成功代替网站 PHP 验收。
  • 最少披露：如需要运行时证据，由管理员通过已有受保护的诊断路径核对版本与这一项设置；仅记录必要字段，不新增公开 phpinfo 或调试端点。本页不提供注入网站的检测代码。
